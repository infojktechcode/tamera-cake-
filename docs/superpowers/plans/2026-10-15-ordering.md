# Phase 3: Ordering Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A customer can build a cake step-by-step, add pastries to the same cart, upload reference photos, pick a deliverable date, and place the order via a server route that computes all prices and deposit on the server. On success they land on `/order/[number]` confirmation with a confetti animation and a WhatsApp link carrying the order summary.

**Architecture:** A multi-step cake builder (`/order/cake?flavour=<id>`) driven by URL query state + `sessionStorage` sync, a pastry browser with quantity steppers, a unified client cart persisted to `sessionStorage`, and a single protected server action `createOrder` that reads prices/tiers/zones/dates from the DB, validates with Zod, inserts via the service-role client, and returns `{ ok: true, order_number }`. The cart drawer and confirmation page use Motion 14 wrappers (`PageTransition`, `ScaleIn`, `Stagger`). Photos upload through signed URLs (`/api/upload`) — 3 file max, 5 MB, JPG/PNG/WebP, compressed client-side before send.

**Tech Stack:** Next 16 PPR, TypeScript strict, Tailwind + shadcn/ui, Motion 14, Supabase (anon public client + service role on server), Zod, React Client components for interactive state.

**Spec:** `Agent.md` (Phase 3 — Ordering, lines 252–275; Screens §6.1 public; Rules §5; Pricing §5; Key logic §5).

## Global Constraints

- All money stored/computed as integer KES on the server (spec §5 rule 6).
- Never trust client prices: server re-computes cake price = `flavour.price_per_kg * size_kg + tier.extra_fee`; pastry line = `unit_price * qty`; deposit = `deposit_percent`% of total when any cake ≥ `deposit_threshold_kg` or tier ≠ Simple; delivery fee from zone.
- `export const dynamic` is forbidden — use `"use cache"` fetchers + `<Suspense>` for anything blocking prerender.
- Client components may NOT import `createServiceClient()` (no SUPABASE_SECRET_KEY in the browser) — orders go through a server route handler using `getServerSideSupabase()` (cookie-aware) for the customer record lookup, but inserts use the service-role client.
- Phone normalisation already exists (`normalizePhone` → `2547XXXXXXXX`).
- Env: `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_SHOP_WHATSAPP=+254714965716`, `SUPABASE_SECRET_KEY`.
- Touch targets ≥ 44 px; mobile first at 360 px.
- `wa.me` links only open a chat — customer presses send; README note stays.
- Photo compression: use browser `canvas` resize to max 1600×1600, JPEG quality 0.8 before upload.

## Review Focus

- **Order submission with mixed items:** a cake + 2 pastries in one order; server must insert `orders`, `order_items` (cake + pastry SKUs), `cake_details` (only for the cake line), all prices copied at creation.
- **Deposit boundary:** 3 kg cake with Simple tier → no deposit; 2 kg cake with Themed tier → 50% deposit; a 3 kg cake with Simple tier triggers deposit even though tier is Simple (threshold is about kg not tier).
- **Date rules at creation:** blocked date → reject; within lead time → reject; daily cake limit exceeded → reject; the rule functions exist in `rules.ts` but must be wired into the order route with live counts from `cake_load_for_date`.
- **Design tier `requires_quote`:** sets `price_needs_quote = true`; total starts as base price (before tier markup) and the shop confirms later — must NOT compute deposit on a quote-only cake.
- **Photo upload over-limit:** 4th file is silently dropped client-side; 5 MB overflow rejected server-side with a clear message.

### Task 5: Cart page + server order route (the critical one)

**Files:**
- Create: `src/app/(public)/checkout/page.tsx` — order summary (cakes + pastries), delivery selector, total + deposit, phone/name, "Place order" button.
- Create: `src/app/api/orders/route.ts` — protected POST, validates, computes prices on server, inserts, returns order number.
- Create: `src/lib/validators/order.schema.ts` — Zod schema for the incoming cart + customer input.

**Interfaces:**
- Consumes: cart types (Task 2), `createServiceClient` (server-only), `cakePrice`, `depositRequired`, `orderTotal` from `pricing.ts`, `checkDateNeeded` from `rules.ts`, Zod.
- Produces: the order record; client navigates to `/order/[number]`.

The server route is the **security boundary**:
```
1. Parse + Zod validate the payload (cart items + customer phone/name + date/time + zone).
2. Fetch `cake_flavours`, `cake_sizes`, `design_tiers`, `delivery_zones`, `settings` by ID from the DB — ignore any price in the payload.
3. For each cake: look up flavour/tier/size, compute price = `flavour.price_per_kg * size_kg + tier.extra_fee`; if tier.requires_quote → set `price_needs_quote = true`, total is base only.
4. For each pastry: look up product, compute line = `unit_price * qty`.
5. Compute subtotal, delivery_fee (zone fee; pickup = 0), total = subtotal + delivery_fee.
6. Deposit = `depositRequired({ anyCakeOverThreshold: any cake.kg ≥ deposit_threshold_kg, anyNonSimpleTier: any cake.tier ≠ Simple })`.
7. checkDateNeeded against live `blocked_dates` + `cake_load_for_date(date)` + `daily_cake_limit`.
8. Normalize phone; upsert customer; insert `orders` + `order_items` + `cake_details`; write `activity_log` rows.
9. Return `{ ok: true, order_number }`.
```

- [ ] **Step 1: Write failing tests** (stub the DB calls): schema rejects `unitPrice` override; `cakePrice` uses DB price not payload; `depositRequired` triggers on 3 kg Simple; `checkDateNeeded` rejects blocked date / within lead time / full day; server route rejects `unitPrice` tampered to KES 1.

- [ ] **Step 2: Run → RED.**

- [ ] **Step 3: Implement** the route + schema + checkout page. Use `getServerSideSupabase` for customer lookup; `createServiceClient` for inserts. Return 400 on validation failure, 500 on compute error. Checkout page POSTs JSON, shows spinner, redirects on success.
